# SQLite 기반 법률정보 지식베이스 설계

작성일: 2026-04-15

## 1. 전환 목적

현재 POC는 사용자가 질문하면 국가법령정보 Open API를 즉시 조회하고, Gemini가 검색어와 답변을 만드는 흐름이다. 이 방식은 다음 문제가 있다.

- 사용자가 기대하는 것은 조회 결과가 아니라 바로 이해 가능한 답변이다.
- Gemini API 사용량 제한이 발생하면 답변 품질이 급격히 떨어진다.
- 질문 때마다 외부 API와 LLM 호출에 의존하므로 응답 안정성이 낮다.
- 공식 근거를 조문 단위로 검증하고 재사용하기 어렵다.

따라서 1차 구조를 다음처럼 바꾼다.

```text
국가법령정보 Open API
→ 핵심 법령 수집
→ 조문 단위 파싱
→ SQLite 저장
→ 질문 분류
→ SQLite 근거 검색
→ 답변 생성
→ 공식 근거 표시
```

국가법령정보 API는 실시간 답변용이 아니라 공식 데이터 갱신용으로 사용한다. 답변은 SQLite에 저장된 조문, 주제, 답변 템플릿을 근거로 만든다.

## 2. 1차 범위

처음부터 전체 법령, 판례, 해석례를 모두 수집하지 않는다. 우선 소상공인 질문에 자주 연결되는 핵심 법령 10개를 대상으로 한다.

| 순번 | 법령 | 1차 활용 주제 |
|---:|---|---|
| 1 | 상가건물 임대차보호법 | 상가 계약, 계약갱신, 권리금, 보증금, 원상복구 |
| 2 | 민법 | 계약, 임대차, 채권, 손해배상, 해지 |
| 3 | 근로기준법 | 근로계약, 임금, 휴게, 해고 |
| 4 | 최저임금법 | 최저임금, 임금 계산 |
| 5 | 근로자퇴직급여 보장법 | 퇴직금, 퇴직급여 |
| 6 | 전자상거래 등에서의 소비자보호에 관한 법률 | 온라인 판매, 청약철회, 환불 |
| 7 | 소비자기본법 | 소비자 분쟁, 피해구제 |
| 8 | 식품위생법 | 음식점, 카페, 인허가, 영업정지 |
| 9 | 소액사건심판법 | 미수금, 소액 분쟁 |
| 10 | 행정절차법 | 처분 사전통지, 의견제출, 행정절차 |

2차 확장 대상은 판례, 법령해석례, 행정심판례, 행정규칙, 자치법규다.

## 3. 데이터 수집 원칙

### 3.1 공식 출처

1차 원천은 국가법령정보 공동활용 Open API다. 수집 시 아래 정보를 반드시 남긴다.

- 법령명
- 법령 ID 또는 MST
- 시행일
- 소관부처
- 조문 번호
- 조문 제목
- 조문 본문
- 수집 일시
- 원문 확인 URL 또는 API 요청 식별 정보

API 키와 OC 값은 `.env.local`에만 저장한다. SQLite DB, 문서, GitHub, 로그에는 저장하지 않는다.

### 3.2 수집 방식

수집기는 사용자 질문 시 실행하지 않는다. 관리자가 필요할 때 실행하는 배치 작업으로 둔다.

```text
npm run kb:fetch
```

1차 구현에서는 다음 순서로 동작한다.

1. 핵심 법령명 목록을 읽는다.
2. 국가법령정보에서 법령 목록을 검색한다.
3. 법령 ID 또는 MST를 확보한다.
4. 법령 본문 또는 조항호목 API로 조문을 가져온다.
5. 조문을 정규화해 SQLite에 저장한다.
6. 수집 결과를 요약 리포트로 남긴다.

수집 리포트에는 “수집 성공, 조문 수, 빈 본문 수, 중복 조문 수, 확인 필요 항목”을 포함한다.

## 4. SQLite 스키마 초안

SQLite는 POC에서 실서비스형 구조를 검증하기 위한 저장소다. Excel처럼 표로 확인할 수 있고, 나중에 PostgreSQL이나 검색엔진으로 옮기기 쉽다.

### 4.1 laws

법령 단위 메타데이터를 저장한다.

| 컬럼 | 설명 |
|---|---|
| id | 내부 ID |
| law_name | 법령명 |
| law_id | 국가법령정보 법령 ID |
| mst | 법령 마스터 번호 |
| ministry | 소관부처 |
| effective_date | 시행일 |
| source_url | 원문 확인 URL |
| fetched_at | 수집 일시 |

### 4.2 articles

조문 단위 데이터를 저장한다.

| 컬럼 | 설명 |
|---|---|
| id | 내부 ID |
| law_id | laws.id |
| article_no | 조문 번호 |
| article_title | 조문 제목 |
| article_text | 조문 본문 |
| chapter_title | 장·절 제목 |
| effective_date | 시행일 |
| normalized_text | 검색용 정규화 본문 |

### 4.3 topics

사용자 질문과 연결할 업무 주제를 저장한다.

| 컬럼 | 설명 |
|---|---|
| id | 내부 ID |
| topic_name | 주제명 |
| description | 설명 |
| example_questions | 예시 질문 JSON |

초기 주제 예시는 다음과 같다.

```text
상가 계약 전 검토
계약갱신
권리금
원상복구
보증금 반환
근로계약서
주휴수당
퇴직금
환불 요청
온라인 판매 청약철회
식품위생 인허가
영업정지 처분
미수금 지급명령
```

### 4.4 article_topics

조문과 주제의 연결 관계를 저장한다.

| 컬럼 | 설명 |
|---|---|
| article_id | articles.id |
| topic_id | topics.id |
| weight | 관련도 |
| memo | 연결 사유 |

1차 구현에서는 수동 규칙으로 연결한다. 예를 들어 `상가`, `임대차`, `권리금`, `계약갱신`, `보증금` 키워드가 포함된 조문은 상가 임대차 관련 주제로 연결한다.

### 4.5 answer_templates

주제별 기본 답변 골격을 저장한다. Gemini가 막혀도 이 템플릿으로 답변을 제공한다.

| 컬럼 | 설명 |
|---|---|
| id | 내부 ID |
| topic_id | topics.id |
| answer_title | 답변 제목 |
| answer_outline | 답변 골격 |
| checklist_json | 체크리스트 JSON |
| caution_text | 주의 문구 |

예시:

```text
주제: 상가 계약 전 검토
답변 골격:
상가 계약 전에는 보증금과 월차임, 계약기간, 갱신 조건, 권리금,
원상복구, 관리비, 업종 제한, 중도해지 조건을 확인해야 합니다.
```

## 5. 질문 처리 흐름

### 5.1 기본 흐름

```text
사용자 질문
→ 질문 정규화
→ 주제 후보 찾기
→ SQLite 조문 검색
→ 답변 템플릿 선택
→ 조문 근거 결합
→ Gemini 요약 선택 적용
→ Risk Guard
→ 화면 출력
```

Gemini는 필수 단계가 아니다. Gemini가 정상 동작하면 찾은 근거를 쉬운 문장으로 다듬고, 429가 나면 SQLite와 템플릿만으로 답한다.

### 5.2 예시 흐름

질문:

```text
상가 계약 전 검토 사항이 있다면?
```

처리:

```text
주제: 상가 계약 전 검토
검색어: 상가, 계약, 임대차, 보증금, 권리금, 원상복구, 계약갱신
법령 후보: 상가건물 임대차보호법, 민법
답변 템플릿: 상가 계약 전 검토
```

출력:

```text
상가 계약 전에는 보증금과 월차임, 계약기간, 갱신 조건, 권리금,
원상복구, 관리비, 업종 제한, 중도해지 조건을 먼저 확인해야 합니다.

체크리스트
1. 임대차 목적물 주소와 실제 사용할 공간 확인
2. 보증금, 월차임, 관리비, 부가세, 연체이자 확인
3. 계약기간과 갱신 조건 확인
4. 권리금 약정과 시설 인수 범위 확인
5. 원상복구 기준 확인
6. 업종 제한과 인허가 가능성 확인
7. 중도해지, 양도, 전대 조건 확인

근거 후보
- 상가건물 임대차보호법 관련 조문
- 민법 임대차 관련 조문
```

## 6. 화면 구조 변경

현재 화면은 검색 결과 중심으로 보인다. SQLite 지식베이스 전환 후에는 아래 순서로 바꾼다.

1. 답변
2. 체크리스트
3. 공식 근거
4. 상담 준비
5. HWP/Excel 복사용

공식 근거는 답변보다 위에 두지 않는다. 사용자가 먼저 필요한 것은 “무엇을 확인해야 하는지”이고, 근거는 그 다음 검증 자료다.

## 7. 오류 처리

| 상황 | 처리 |
|---|---|
| Gemini 429 | SQLite 템플릿 답변으로 계속 진행 |
| 국가법령정보 API 장애 | 기존 SQLite 데이터로 계속 진행하고 갱신 실패 기록 |
| 조문 본문 없음 | 수집 리포트에 확인 필요로 표시 |
| 질문 주제 미분류 | 일반 소상공인 법률정보 질문으로 처리하고 추가 질문 제시 |
| 근거 부족 | 답변에 “공식 근거 추가 확인 필요” 표시 |

## 8. 검증 질문

1차 검증은 아래 질문 3개로 한다.

```text
1. 상가 계약 전 검토 사항이 있다면?
2. 아르바이트 근로계약서 작성 시 확인할 것은?
3. 고객 환불 요청이 들어오면 어떤 기준을 확인해야 하나?
```

성공 기준:

- 답변이 검색 결과 나열이 아니라 실무형 문장으로 시작한다.
- 체크리스트가 5개 이상 나온다.
- 관련 법령 후보가 표시된다.
- Gemini API가 막혀도 기본 답변이 나온다.
- API 키나 OC 값이 화면, 로그, GitHub에 노출되지 않는다.

## 9. 구현 단계 제안

1. SQLite DB 초기화 스크립트 작성
2. 핵심 법령 10개 목록 파일 작성
3. 국가법령정보 법령 목록 조회 수집기 작성
4. 법령 본문·조문 파서 작성
5. topics와 answer_templates seed 작성
6. SQLite 검색 API 작성
7. 기존 Gemini Agent 흐름을 SQLite 우선 흐름으로 교체
8. 검증 질문 3개 자동 테스트 작성
9. 화면 탭 순서와 문구 수정

## 10. 보안과 운영 원칙

- `.env.local`은 GitHub에 올리지 않는다.
- SQLite DB에는 API 키, OC, 개인정보, 계약서 원문을 저장하지 않는다.
- 사용자가 입력한 질문은 기본적으로 저장하지 않는다.
- 수집 원자료와 파싱 결과는 출처와 수집일을 남긴다.
- 최종 답변에는 법률 자문이 아니라 법률정보 탐색 보조라는 고지를 유지한다.

## 11. 보류 사항

아래는 1차 구현에서 제외한다.

- 전체 법령 일괄 수집
- 판례 본문 대량 수집
- 벡터DB 도입
- 사용자 계약서 원문 업로드
- 답변 이력 저장
- 변호사 상담 연결

1차 목표는 “SQLite에 저장된 공식 법령 조문과 주제 템플릿만으로도 답변다운 답변이 나오는지” 확인하는 것이다.
